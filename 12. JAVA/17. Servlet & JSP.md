
# Servlets & JSP

## Le problème de départ

Un navigateur envoie une requête HTTP à un serveur. Le serveur doit répondre avec du HTML généré dynamiquement — par exemple, afficher le feed d'un utilisateur avec ses vrais posts depuis la base de données.

C'est exactement ce que font les **Servlets** et les **JSP** ensemble.

---

## Les trois acteurs

```
Navigateur  ──requête──►  Tomcat  ──appelle──►  Ta Servlet
Navigateur  ◄──réponse──  Tomcat  ◄──retourne── Ta Servlet / JSP
```

- **Tomcat** : le serveur. Il reçoit les requêtes et les distribue à la bonne Servlet selon l'URL.
- **Servlet** : classe Java qui traite la requête (récupère les données, applique la logique).
- **JSP** : fichier HTML dans lequel on injecte des données pour générer la réponse.

---

## La Servlet

C'est le **contrôleur**. Elle reçoit la requête, fait le travail, puis transmet le résultat à la JSP.

```java
@WebServlet("/register")  
public class RegisterController extends HttpServlet  {  
  
    private RegisterUseCase registerUseCase;  
  
    @Override  
    public void init() throws ServletException {  
        super.init();  
        this.registerUseCase = ServiceLocator.getInstance().getRegisterUseCase();  
    }  
  
    @Override  
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {  
        req.getRequestDispatcher("/WEB-INF/views/register.jsp").forward(req, resp);  
    }  
  
    @Override  
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {  
          
        String login = req.getParameter("login");  
        String email = req.getParameter("email");  
        String password = req.getParameter("password");  
        String confirmPassword = req.getParameter("confirm");  
  
        String error = registerUseCase.validate(login, email, password, confirmPassword);  
        if (error == null) {  
            resp.sendRedirect("/login");  
        } else {  
            req.setAttribute("error", error);  
            req.getRequestDispatcher("/WEB-INF/views/register.jsp").forward(req, resp);  
        }  
    }  
}
```

### doGet vs doPost

|Cas|Méthode|
|---|---|
|Afficher une page (ex: le feed)|`doGet`|
|Soumettre un formulaire (ex: créer un post)|`doPost`|

## La JSP

C'est la **vue**. Elle ressemble à du HTML, avec des blocs Java embarqués pour afficher les données préparées par la Servlet.

```jsp
<%@ page contentType="text/html;charset=UTF-8" %>
<%@ page import="java.util.List" %>
<%@ page import="com.exemple.model.Post" %>

<!DOCTYPE html>
<html>
<body>
    <h1>Feed</h1>

    <%
        // On récupère la liste déposée par la Servlet
        List<Post> posts = (List<Post>) request.getAttribute("posts");

        if (posts == null || posts.isEmpty()) {
    %>
        <p>Aucun post.</p>
    <%
        } else {
            for (Post post : posts) {
    %>
        <div>
            <strong><%= post.getAuteur() %></strong>
            <p><%= post.getContenu() %></p>
        </div>
    <%
            }
        }
    %>
</body>
</html>
```

- `<% %>` — **scriptlet** : bloc de code Java exécuté côté serveur
- `<%= %>` — **expression** : affiche la valeur directement dans le HTML
- `<%@ page import="..." %>` — importe une classe Java dans la JSP (comme un `import` normal)
- `request` est un objet disponible automatiquement dans toute JSP, il correspond au `HttpServletRequest` de la Servlet

## Passer des données : setAttribute / getAttribute

```java
// Dans la Servlet : on dépose une valeur dans la requête
req.setAttribute("posts", posts);

// Dans la JSP : on la récupère avec EL
${posts}

// Dans une autre Servlet (si besoin) :
List<Post> posts = (List<Post>) req.getAttribute("posts");
```

Pense à `setAttribute` comme déposer un objet dans une enveloppe avant de la transmettre à la JSP.

---

## Forward vs Redirect

### Forward

```java
req.getRequestDispatcher("/WEB-INF/views/feed.jsp").forward(req, resp);
```

Tomcat transfère la requête en interne à la JSP. L'URL dans le navigateur **ne change pas**. Les données déposées avec `setAttribute` **sont conservées**. A utiliser pour afficher une JSP.

### Redirect

```java
resp.sendRedirect("/feed");
```

Le serveur demande au navigateur de faire une **nouvelle requête** vers une autre URL. L'URL **change**. Les données `setAttribute` **sont perdues**. A utiliser après un POST (ex: après avoir créé un post, on redirige vers le feed).

```
Forward  : Navigateur → Servlet → [interne] → JSP
Redirect : Navigateur → Servlet → "va là-bas" → Navigateur → nouvelle requête
```

> Après un `sendRedirect`, toujours ajouter `return` pour stopper l'exécution.

```java
resp.sendRedirect("/feed");
return;
```

## La session

HTTP est sans mémoire : chaque requête repart de zéro. La session permet de **retenir des informations entre les requêtes** — typiquement, l'utilisateur connecté.

```java
// Connexion : on stocke l'utilisateur dans la session
HttpSession session = req.getSession();
session.setAttribute("userConnecte", user);

// Sur une autre page : on vérifie qu'il est connecté
User user = (User) session.getAttribute("userConnecte");
if (user == null) {
    resp.sendRedirect("/login");
    return;
}

// Déconnexion
session.invalidate();
```

---

## Cycle de vie d'une Servlet

```
Tomcat démarre → instancie la Servlet (une seule fois) → init()
                         │
          à chaque requête → service() → doGet() ou doPost()
                         │
Tomcat s'arrête → destroy()
```

Une seule instance est créée et partagée entre toutes les requêtes. Ne jamais stocker des données utilisateur dans un champ de la Servlet — utilise la session ou la requête.

## Structure de projet

```
src/main/
  java/
    servlet/      FeedServlet.java, LoginServlet.java...
    model/        Post.java, User.java...
    service/      PostService.java...
    dao/          PostDao.java...
  webapp/
    WEB-INF/
      views/      feed.jsp, profil.jsp...   ← inaccessibles directement
    index.jsp
```

Les JSP dans `WEB-INF/` ne sont pas accessibles par une URL directe. Seule une Servlet peut les atteindre via `forward`. Ca force à toujours passer par le contrôleur.
